# [Plan] Experiment: does a rerank input-token cap bring KB rerank inside the 2s seam budget?

> **Created:** 2026-09-24 16:46
> **Branch:** develop
> **Package Manager:** bun

---

## Spec

**Objective** — Rerank at candidateLimit 15 lifts the KB goldset from Hit@5 0.93 / Recall@5 0.69 to 0.95 / 0.76.
Cold p90 is 4345ms against a 2s seam budget (PLAN-12-27-43 Outcome). The reranker is sent each candidate's
best chunk, head-truncated only at the context budget (4096 − 512 − query tokens), so a ~900-token chunk goes in
whole. This experiment adds an opt-in env cap `QMD_RERANK_MAX_DOC_TOKENS` and measures quality and cold
latency at caps 128/256/512/full with N=15. It answers one question: does any cap meet the budget without
losing the quality gain?

**Success Criteria**
- [ ] `QMD_RERANK_MAX_DOC_TOKENS=<n>` limits each rerank doc to at most n tokens. Unset, rerank behaves exactly as before. A unit test covers both.
- [ ] The rerank cache never serves a score computed under a different cap. Under a cap, the cache key differs from the uncapped key, and a test covers it.
- [ ] Token-length distribution (median/p90/max) of the best chunks that N=15 sends to the reranker, over the 39 golden queries.
- [ ] Table for cap ∈ {128, 256, 512, full} at N=15, each run cold on a fresh cache-emptied copy with query 1 dropped. Columns: Hit@5, Recall@5, MISS ids, median ms, p90 ms. The full row reproduces the earlier N=15 quality: 0.95 / 0.76.
- [ ] One verdict line: the smallest cap with Hit@5 ≥ 0.95, Recall@5 ≥ 0.74 and p90 ≤ 2000ms, or "none". If none, give ms/chunk at each cap.
- [ ] Results go in `## Outcome` and a NOTE. The real index (`~/.cache/qmd/index.sqlite`) stays unchanged: its `llm_cache` count is the same before and after.

## Decisions
- Assumed: head truncation first. The best chunk already has the most query-term hits, so its head is a reasonable proxy. A keyword-centred window is Slice 03, run only if head truncation fails the quality bar at the cap that meets the latency bar.
- Assumed: the cap is an instance field `LlamaCpp.rerankMaxDocTokens` read from env in the constructor, not a static IIFE. `RERANK_CONTEXT_SIZE` is a static evaluated at import, so a test cannot set the env after import. A constructor read is testable with `new LlamaCpp({})`.
- Assumed: the cap enters the cache key by suffixing `cacheModel` (for example `…#max256`) only when `llm.rerankMaxDocTokens` is set. Unset keeps today's keys, so the warm cache survives. GOTCHA: without this, a capped run on a warm index replays uncapped scores and reads as a free win.
- Assumed: one cold run per cap at cl=15 gives both quality and latency. A capped rerank score depends on the cap, so the old cl=40 dump cannot replay caps offline.
- Assumed: code lands on a feature branch (`feat/rerank-max-doc-tokens`). A PR goes up only if the verdict passes. A "none" verdict discards the branch and keeps only the NOTE, since shipping an env nobody should set is dead config.
- Assumed: same bar as PLAN-12-27-43 (Hit@5 ≥ 0.95, Recall@5 ≥ 0.74, p90 ≤ 2000ms) and the same conditions (daemon up, Metal, fresh `.backup` copy with `llm_cache` emptied).
